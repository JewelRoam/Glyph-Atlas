# 字脉 · Glyph Atlas

**人类书写体系演化可视化**

把世界上所有书写体系的演化关系画成一张可以缩放的有向图，
并让同一个字在数千年里连续变形。

<sub>193 个书写体系（另有奇普） · 12 个独立起源 · 88 个今仍使用 · 37 条血统轨道</sub>

</div>

---

## 这是什么

人类在几千年里只**独立发明过寥寥几次**文字：苏美尔、埃及、中国、
印度河、中美洲。其余几乎所有书写体系——从腓尼基字母到天城文，
从阿拉伯文到谚文——都是这几次发明的后代，通过借用、改造与传播，
长成一棵覆盖全球的大树。

字脉想把这棵树画出来，并且让它**动起来**。为此它有两个尺度：

| 尺度 | 视图 | 你在看什么 |
| --- | --- | --- |
| 宏观 | **演化图谱** `Macro` | 全部书写体系的有向图。横轴是年代，纵轴按十二个谱系分泳道，连线是"衍生自"。可缩放、可拖拽，悬停任一节点即高亮其全部祖先与后代。 |
| 微观 | **时间街景** `Micro` | 选定一条血统轨道，沿时间前后行走。中心字形在两站之间连续变形，身后留下下一站的残影；两侧是这条街上的邻居，底部站点尺可跳到任意一站。 |
| 索引 | **文字总表** `Index` | 可按谱系筛选、按年代或名称排序、按名称搜索的全量对照表，带使用国家 / 地区与现行状态。 |

## 快速开始

```bash
npm install
npm run dev          # 本地开发，默认 http://localhost:5173
npm run build        # 数据校验 → 类型检查 → 打包到 dist/
npm run preview      # 预览打包产物
```

其它可用的脚本：

```bash
npm run validate     # 只跑数据校验（新增书写体系后先跑这个）
npm run lint         # oxlint
npm run typecheck    # tsc -b
npm run check        # validate + lint + typecheck，提交前一键跑
npm run audit:coverage      # 血统入口覆盖报告（不阻塞构建）
npm run audit:coverage:json # 同一份报告，输出 JSON
npm run shots        # 视觉校对：把三屏 + 移动端拍成图（按需装 Playwright，见下）
```

`npm run build` 会先执行数据校验，**数据错误会直接阻塞构建**。

### 视觉校对（可选）

`npm run shots` 会把三个页面、一张选中详情、一屏移动端各拍一张，
顺便收集 console 报错，图默认落在 `work/shots/`（已在 .gitignore 里）。
Playwright 连同浏览器有几百 MB，不适合放进 `devDependencies` 让每个克隆的人
都下载一遍，所以它按需安装：

```bash
npm run build
npm i --no-save playwright && npx playwright install chromium
npm run shots
```

优先用本机已有的 Edge / Chrome，找不到才用 Playwright 自带的 Chromium。

### 字体审看台（可选）

"这款字画的是不是这套文字"机器判不了：字族名对得上、覆盖表里也有这些码位，
字面仍可能是另一套文字的写法。`tools/font-sheet.mjs` 把每个体系按它真正会用的
字族铺成对照表，一行一个体系（字母表铺前若干格，没有字库的体系贴图版），人工
过一眼：

```bash
npm run build
node --import ./tools/register-ts.mjs tools/font-sheet.mjs work/font-sheet
# → work/font-sheet/tile-01.png …，14 张图看完 194 个体系
```

看图得出的结论写进 `tools/font-verdicts.tsv`：一行一个体系，记 id、结论
（`ok` / `wrong` / `blank` / `todo`）、当前字族、以及需要交代时的理由。
`tools/audit-font-verdicts.mjs` 已挂在 `npm run validate` 上：新增体系不补一行
就报错，`wrong`（已知画错）直接让构建失败——不允许"知道错了还发布"；第三列的
字族和代码里实际用的不一致也报错，换了字体就得重新过一遍审看台。

截图不看 `vite preview`：构建产物挂在仓库名前缀下（`vite.config.ts` 的 `base`），
而 `vite preview` 只把 `dist` 挂在根路径，`/Glyph-Atlas/assets/*.js` 会落到单页
回退、以 HTML 返回，页面白屏。`tools/screenshot.mjs` 自己起一个静态服务，照
GitHub Pages 的挂法伺服 `dist`，拍到的就是上线的那一份。

## 图谱是怎么排出来的

宏观图不是力导向布局（force layout）——那会把"公元前 3000 年"和"公元 300 年"
摆在一起，对年代叙事是灾难。它是一张手工控制的坐标图：
**横轴是年代，纵轴是谱系**，位置本身就是信息。

### 两层结构

| 层 | 内容 | 跟着缩放吗 |
| --- | --- | --- |
| 坐标系层 | 泳道底色、年代竖线、演化边、节点与生命线 | 会。这就是"图"本身 |
| 陈设层 | 左侧谱系名、顶部年代刻度 | 不会。属于地图注记，字号恒定 |

节点的中文名留在坐标系层里，但字号按 `1/k` 反向补偿，屏幕上始终是 11.5px；
再缩下去就交给下面那套取舍机制，而不是放任文字变小或叠在一起。

### 横向：等比例线性时间轴

横轴就是年代本身：`x = (年 − 前3300) × 每年宽度`（`lib/timescale.ts`）。
全站时间域 −3300 – 2030 共 5330 年，公元前因此自然占据 62% 的横向空间，
任意两段年代的横向距离之比都等于真实年代之比——看图的人可以直接用眼睛
比较"隔了多久"。

这里走过一段弯路。起初为了少占几行，时间轴是按标签密度分配宽度的分段轴：
把时间域切成九段，每段宽度按"这一段要放多少标签"来分。代价是公元前 3300 年
只剩 34% 的宽度，读起来像是"公元前被压缩了"。年代轴一旦不等比例，位置就
不再是可靠的信息——横向坐标只能表示"先后"，不能表示"多久"。所以改成等比例，
密集期不再靠拉伸时间轴解决，而是交给泳道内分行、缩放平移与标注取舍这三件事。
代价是整张图更宽更高，桌面总览比例落在 0.20–0.37，窄屏更低；
首次进入与"总览"按钮都会依此重新适配并居中。

### 纵向：泳道 + 贪心分行

`lib/layout.ts` 把十二个谱系排成泳道（顺序由 `FAMILY_ORDER` 决定），
泳道内部按时间顺序贪心分行：一行放不下就换行（`ROW_H = 36`）。
布局只需要一个"这个名字占多宽"的函数（`LabelWidth`），
它不知道字体、缩放和 canvas，因此同样的布局在服务端也能算。

### 标注取舍：宁可少显示，也不叠字

缩得太小时，屏幕上根本塞不下全部名字。`AtlasGraph` 的做法是**先判定、再决定画不画**：
按优先级（今仍使用 > 宗教用 > 历史 > 消亡 > 未破译）依次给每个名字占位，
先试节点右侧，右侧被占就翻到左侧（文字改右对齐），两侧都撞上才折叠不画。
只有真的折叠了名字时，页脚才会留一行"另 N 个重叠标注已折叠"；
点"标注"按钮可以把它们整个关掉，只看星座一样的节点与连线。

两个坑都踩过，写在这里免得再踩：

1. **碰撞判定要用真实行盒高度。** 11.5px 的中文实测行盒是基线上方 12px、
   下方 4px，共 16px；拿 `font-size` 当高度会出现"判定通过、肉眼叠字"。
2. **布局预留与取舍判定必须同源。** 布局按 `labelWidth`
   （`measureText` 实测宽度 ÷ `NOMINAL_K`）预留横向空间，`labelPlan`
   用同一个 `measureText` 判碰撞；任何一处改用估算（比如按字数 × 字号），
   就会出现"布局以为放得下、屏幕上却撞车"。`NOMINAL_K` 是偏乐观的旋钮：
   调大布局更紧凑、折叠更多，调小图更高更空、折叠更少。

### 调参速查

想改图的手感，先看这几处——它们都是有意留出来的旋钮：

| 想改什么 | 去哪里改 | 现值 |
| --- | --- | --- |
| 图形总宽随窗口伸缩的倍率 / 上下限 | `AtlasGraph.tsx` `AXIS_WIDTH_RATIO` / `_MIN` / `_MAX` | 2.6 / 2100 / 4600 |
| 按哪个缩放比例预留标签宽度 | `AtlasGraph.tsx` `NOMINAL_K` | 0.48 |
| 节点名在屏幕上的字号 | `AtlasGraph.tsx` `NODE_LABEL_PX` | 11.5 |
| 相邻名字之间的最小空隙 | `AtlasGraph.tsx` `LABEL_GAP` | 6 |
| 泳道行高 / 泳道间留白 | `lib/layout.ts` `ROW_H` / `LANE_PAD` | 36 / 16 |
| 时间域（线性轴的起止年） | `lib/timescale.ts` `TIME_DOMAIN` | 前3300 – 2030 |
| 缩放上下限 | `AtlasGraph.tsx` `ZOOM_MIN` / `ZOOM_MAX` | 0.18 / 6 |
| 泳道顺序 | `lib/layout.ts` `FAMILY_ORDER` | 12 条 |
| 谱系配色 / 中文名 | `lib/time.ts` `FAMILY_COLOR` / `FAMILY_LABEL` | 12 条 |

## 数据模型

### WritingSystem —— 图谱里的一个节点

```ts
{
  id: 'phoenician',              // 唯一 id，用作 parents 的引用
  nameZh: '腓尼基字母',
  nameEn: 'Phoenician Alphabet',
  alias: ['腓尼基文'],            // 可选，用于搜索
  origin: 'derived',             // independent | derived | influence | invented
  parents: ['proto-sinaitic'],   // 父系 id 列表（有向边的来源）
  dateFrom: -1050,               // 负数表示公元前
  dateTo: -200,                  // null 表示至今仍在使用
  family: 'levant',              // 十二个泳道之一
  region: '黎凡特海岸',
  countries: ['黎巴嫩', '叙利亚'], // 今天（或历史上）主要使用国家 / 地区
  type: 'abjad',                 // 类型学分类
  status: 'extinct',             // 使用状态
  direction: 'rtl',              // 可选
  unicodeBlock: 'Phoenician U+10900',
  sample: '𐤀',                   // 渲染用的样本字符
  fontFamily: 'Noto Sans Phoenician',
  note: '希腊、拉丁、阿拉伯诸系的共同祖先。',
  lineageEntry: { lineageId: 'aleph', stopId: 'phoenician' }, // 可选：首选入口
  sourceRefs: ['https://en.wikipedia.org/wiki/Phoenician_alphabet'], // 可选：通用参考
}
```

| 字段 | 作用 | 注意 |
| --- | --- | --- |
| `id` | 节点主键 | 全表唯一，改动会打断 `parents` 引用 |
| `origin` | 起源性质 | 有 `parents` 就不能写 `independent`（校验器会拦） |
| `parents` | 有向边 | 可以多个：接触、混用、多重影响都允许 |
| `dateFrom` / `dateTo` | 时间轴定位与生命线长度 | 约数，学界有分歧时取主流观点 |
| `family` | 泳道 + 配色 | 必须是 `Family` 联合类型里的值 |
| `type` | 类型学分类 | `nonscript` 的记录系统不会进入演化图 |
| `sample` / `fontFamily` | 字形渲染 | 没有 Web 字体时会显示码位名片（见下） |
| `lineageEntry` | 从节点进入血统视图的首选轨道与站点 | 可省略；省略时取第一条经过该体系的轨道 |
| `sourceRefs` | 体系级参考链接 | 字体、Unicode 提案、条目等通用出处 |

### Lineage —— 一条可以"往前走"的街

一条轨道是**同源字位**的序列，它不等于书写体系的传承树：
轨道关心的是"同一个字/同一个音"在各体系里长成什么样。

```ts
{
  id: 'aleph',
  nameZh: '牛头 → 字母 A',
  nameEn: 'Ox head → A',
  mode: 'chain',                 // chain | cognate | pair
  source: '……依据哪份资料认定这几站是同一条线。',
  sourceRefs: [                   // 必填；站点证据缺省时继承
    'https://en.wikipedia.org/wiki/Proto-Sinaitic_script',
    'https://en.wikipedia.org/wiki/Phoenician_alphabet',
  ],
  description: '……一句话说清这条轨道在演示什么。',
  stops: [
    {
      id: 'egyptian-f1',         // 轨道内稳定；未来深链与节点跳转都靠它
      script: 'egyptian',
      label: '牛头（圣书体 F1）',
      phonetic: 'pr / 牛',
      path: 'M50 8 C42 …',
      sourceRef: '……这一站的证据链接',
      asset: { kind: 'path', credit: '……', license: '……' },
    },
    { id: 'phoenician-aleph', script: 'phoenician', label: 'ʾālep', phonetic: 'ʔ', path: 'M30 8 L48 8 …' },
    { id: 'latin-a', script: 'latin', label: 'A', phonetic: 'a', path: 'M50 4 L98 96 …' },
  ],
}
```

站点键写作 `${lineageId}:${stop.id}`。`id` 在轨道内必填且发布后不改；同一轨道
重复经过同一书写体系（例如同一体系的不同书体阶段）时，每个阶段各自有独立的
`id`。`stopsByScript` 与 `lineagesByScript` 把“书写体系 → 轨道 / 站点”反过来
建索引，供从任意图谱节点进入对应的前后演变。`sourceRef` 记单站证据，轨道级
`sourceRefs` 记整条线的参考，站点自己的证据优先；`asset` 记这一站实际使用的
轮廓、图版或字体的来源与授权。三者随站点保存，避免换素材时与谱系脱节。
新增轨道至少要有一条可打开的 `sourceRefs`；只有链接并不等于逐站结论已经定稿，
后续复核仍应优先补到单站证据。

`mode` 决定"往前一步"意味着什么，也决定校验规则：

| mode | 含义 | 站点顺序 | 校验 |
| --- | --- | --- | --- |
| `chain` | 单线传承（牛头 → A） | 按年代递增 | 会检查年代是否倒退 |
| `cognate` | 同源辐射（婆罗米 ka → 各国 ka） | 按叙事顺序，年代会来回跳 | 不检查年代 |
| `pair` | 借字记音（汉字 → 假名） | 母字与借字成对出现 | 不检查年代 |

### 从任意节点进入血统视图（数据契约）

未来的目标不是再造一套详情页，而是让 MACRO 里的任意节点都能打开同一条
“前后演变”界面。数据层已经为此准备好稳定入口，但**目前还没有接入界面**：

```ts
lineageEntryFor(scriptId)      // 默认轨道与站点；无轨道时返回 undefined
lineageHref(scriptId, track?)  // 生成 ?script=…&lineage=…&stop=…
stopRefFromParams(lineage, stop) // 从 URL 参数恢复站点，无效参数返回 undefined
neighboringStopRefs(scriptId)  // 默认入口的前后邻站
lineageStatusFor(system)       // neighbors | standalone | isolated

scriptContextFor(scriptId)     // 一个节点的图关系 + 默认血统上下文
graphChildrenByScript          // scriptId → 图上的直接子节点
```

`scriptContextFor()` 是给未来节点详情复用的统一读模型：

```ts
{
  system,                       // 当前书写体系
  graph: { parents, children }, // parents 有向图里的直接前后关系
  lineage: {                    // 没有任何已核实轨道时整段省略
    entry,                      // 默认轨道站点，可直接定位 MICRO
    previous, next,             // 默认入口在轨道上的前后站
    alternatives,               // 该体系出现的其他轨道入口
  }
}
```

`graph` 和 `lineage` 刻意分成两层：前者回答“这套文字从哪些书写体系而来、又
影响了谁”，后者回答“这个字位在这条已核实的字形链上如何变化”。两层不能互相
冒充，节点详情可以在同一份对象里分别展示，而不必再造第二套模型。`alternatives`
已经按轨道去重，只保留每条轨道的默认站点；同一轨道上的其他书体阶段仍可通过
`stopsByScript` 取得。

入口优先读 `WritingSystem.lineageEntry`，没有指定时取 `lineages` 中第一条经过
该体系的轨道。多轨道节点应明确首选入口，避免数组顺序无意中改变产品语义。
三种状态都是合法的：有前后邻站（`neighbors`）、只有单站（`standalone`）、
没有轨道（`isolated`）。最后一种应打开单体系详情，而不是为了覆盖率伪造链条。
URL 参数只用稳定的 `script`、`lineage`、`stop` id；后续若需要播放位置，可以
再加 `t`，不会改动已有站点键。

等样本覆盖足够后，MACRO 节点详情可以直接消费这份上下文：用
`lineage.entry` 进入对应的 MICRO 街景，用 `previous` / `next` 继续前后行走，
用 `alternatives` 切换其他轨道；没有 `lineage` 的节点则只展示体系级资料。
这样合流不需要迁移素材，也不需要给字形再编一套 id。

### 覆盖审计

```bash
npm run audit:coverage       # 人类可读报告
npm run audit:coverage:json  # 交给脚本或 CI 的 JSON
```

它把“还缺什么”列成补链队列：哪些节点已有可前后行走的入口、哪些只能先以单
体系打开、哪些站点或轨道缺来源、哪些素材缺登记。报告还区分首选入口是
`explicit`（数据里明确指定）还是 `fallback`（按轨道数据顺序回退），并检查
`scriptContextFor()` 返回的 parents / children / 邻站是否与源数据一致。

当前 193 个图谱节点中，96 个已有可前后行走的入口，97 个尚无轨道入口；12 个
独立起源中 3 个已有入口。26 个多轨道节点均已明确首选入口，另有 70 个单轨道
节点使用合法的回退入口。体系级 `sourceRefs` 目前覆盖 12/193 个节点；37 条轨道
都至少登记了一组参考链接，139 个站点均已有来源（站点专属或继承轨道）和素材
登记。无轨道不等于漏数据，尤其对未破译或独立起源体系，必须先有可靠证据才补链。
覆盖率达标后可用 `npm run audit:coverage -- --strict` 把它升级为 CI 门禁。

### 字母场 —— 一整套字母表的形变

街景中心一次只演一个字形。往下还有一块**字母场**：它把两端文字的整套字母
一次性铺开，让每个字母各自对位变形。能这么做的前提是一张手工的对照表
`src/data/letterSlots.ts`：

```ts
SLOTS      = [ { id: 'aleph', label: '牛头 ʾālep' }, … ]   // 格子的全局次序
letterMaps = { phoenician: { aleph: '𐤀', … }, greek: { aleph: 'Α', … } }
```

格子按**同源槽位**排，不按 Unicode 顺序——否则希腊 Γ 会挨着拉丁 C，
可 C 真正的祖形其实是 Γ，而拉丁 F 来自希腊 Ϝ。一个字符可以占两个槽位
（腓尼基 𐤅 同时进 `waw` 与 `digamma`，变形成 Υ 与 Ϝ 两支），两个槽位也可以
指向同一个字形（哈特拉的 `d` 与 `r`，Unicode 名就叫 DALETH-RESH）。

手工表之外还有一层**自动补位**（`rosterFor()`）：字母表、辅音音素文字、
元音附标文字、音节文字、特征文字这几类都有确定的字母清单，手工没核到的字会按
字母身份（忽略大小写与附加符号）各占一格补在后面。补位的格子不参与形变——没有
核实过的同源关系宁可不动，也不硬凑成"原地变形"。

补位不设"只取前多少格"的截断：字母场要铺出这一家字母表的**全部**字母，
左右切换、侧边站点与底部刻度都走同一条补间，新增 / 消失的格子会平滑飞入或
飞出；`tools/audit-rosters.mjs` 跟着 `npm run validate` 一起跑，任何一家的
字表被截断或掉字都会让构建失败。字表里只少两类字——同字母的另一种写法（大小写、
附加符号，占同一格）和 `NON_LETTER_MARKS` 里那些"长得像字其实不是字"的记号
（叠字符号、只能加在别的字母上的修饰记号）。目前最大的一张表是彝文，1165 格；
加拿大原住民音节文字 637 格。

一段轨道上出现哪几格，由两端的**完整字表**并集决定，于是三种情况一目了然：

- 两端都有 → 原地对位形变；
- 只有终点有 → 新字母从下方飞入并放大；
- 只有起点有 → 被淘汰的字母向上缩小飞出。

任意一端有字表就铺字母场：只有一边有（例如"埃及圣书体 → 字母 A"里的圣书体，
或还没核过同源位的两家）时，整场都是增删，两边的字表各自成批飞入 / 飞出，
场下会写明这一段没有核对过的同源字母。

语素文字（汉字、圣书体、玛雅文字）没有字母表，不铺格，仍然只走单字形的街景。

婆罗米系的字母表有三层槽位，走字母场时依次排在前面的是元音：

| 层 | 文件 | 内容 |
| --- | --- | --- |
| 独立元音 | `src/data/svaraSlots.ts` | 18 个 `svara-*`：अ आ इ ī u ū r̥ … 独立成字的元音字母 |
| 依附式元音 | `src/data/matraSlots.ts` | 23 个共享 `matra-*` + 6 个单家 `matra-*`：का कि की 这类写在辅音上的元音符号 |
| 辅音 | `src/data/letterSlots.ts` | `varga-*`：按发音部位排的梵语字音表位 |

**依附式元音**是这一片文字真正日常在用的元音：泰文写作 ะ า ิ ี ุ ู เ แ โ ใ ไ，
高棉写作 ា ិ ី ុ ូ េ ៃ ោ ៅ，爪哇写作 ꦴ ꦶ ꦷ ꦸ ꦺ …。这些符号离开辅音只剩
一道小钩，单独立格既看不出读音、也没法和别家比，所以槽位存的是**符号本身**，
取轮廓时把它挂在各自 `MATRA_BASE` 里的代表基字（一律取自家的 ka）上，
交给 HarfBuzz 整形，取整段连写的轮廓——画出来是 का 而不是 ू，泰文的前置元音
（เ + ก）也会整形到基字前面，拿到该文字里它真正的样子。因为轮廓带着基字，
它的键不能按单字符取，改用 `${文字}#${槽位}`。

有 `svara` / `matra` 两层之后，一段婆罗米系轨道上的格子数才是这家字母表的
全量：泰文 ↔ 老挝文现在是 62 格对 62 格。梵语 33 音之外，各家另有的 ḷa、ḻa、
ṟa、ṉa 等本地音位也各占独立格子；某家没有这种音位时，格子会按新增或消失处理。

格子数在两段之间变化时，网格要换行重排，这里用 FLIP 把每格从旧位置滑到
新位置，连同字母场高度一起过渡，不会整排跳一下。数字都写在表格左上的小字里
（同源 / 新增 / 消失）。

几百格的音节文字表铺开有三四屏高，所以字母场只吃"剩下的高度"：舞台保底
190px（矮屏上中央字形也不会被压扁、压到展签上），字母场按视口减去这段开销
算出自己的上限（150–300px，写进 `--alpha-cap`），超出上限的部分在场内滚动，
`overscroll-behavior` 保持自动，滚到底再继续滚就是整页往下走。

切换血统轨道（顶部标签）走的是交叉淡变：旧街保留到淡出结束，新街同时从
标签次序对应的方向滑入，期间旧街只留画面、不再抢方向键。

## 如何新增一种文字

1. 在 `src/data/writingSystems.ts` 里找到对应的谱系分区，追加一条记录：

```ts
{
  id: 'old-hungarian', nameZh: '古匈牙利文', nameEn: 'Old Hungarian',
  origin: 'influence', parents: ['ogham'], dateFrom: 1000, dateTo: 1600,
  family: 'centralasia', region: '喀尔巴阡盆地', countries: ['匈牙利', '罗马尼亚'],
  type: 'alphabet', status: 'historical', direction: 'rtl',
  unicodeBlock: 'Old Hungarian U+10C80', sample: '𐲀',
  fontFamily: 'Noto Sans Old Hungarian',
  note: '与周边书写体系的接触关系尚有争议。',
},
```

2. 跑校验：

```bash
npm run validate
```

校验器会告诉你三件事——**错误**（阻塞构建）与**提示**（不阻塞）：

- `parents` 指向了不存在的 id
- 声明 `independent` 却又有父系（或声明 `derived` 却没有父系）
- `dateTo` 早于 `dateFrom`、缺国家 / 地区、缺中英文名
- 父系年代晚于子系（提示，年代本身是约数，200 年宽容度）
- 超出全站时间域 `-3300 – 2030`（提示）

3. 回到页面确认它出现在图谱与总表里。
如果样本字符是一片空白或是"码位名片"，说明该文字还没有可用的 Web 字体（见下节）。

## 如何新增一条血统轨道

在 `src/data/lineages.ts` 里追加一条 `Lineage`。先给每个站点一个轨道内唯一的
`id`，再按三种方式之一补字形；同一轨道若重复出现同一书写体系，`id` 不得省略。

**A. 手工矢量路径**——给 `path`，
坐标统一使用 `viewBox="0 0 100 100"`，可以含多个子路径
（例如字母 A 的三角形内孔就是第二条子路径）：

```ts
{ script: 'greek', label: 'alpha（早期）', phonetic: 'a', path: 'M50 8 L94 94 L72 94 …' },
```

**B. 字符 + 自动提取轮廓**——给 `char`，
字体从 `scriptById[stop.script].fontFamily` 取，也可以用 `fontFamily` 单独覆盖：

```ts
{ script: 'tibetan', char: 'ཀ', label: '藏文', phonetic: 'ka' },
```

**C. 历史图版**——没有可靠字体、也没有独立 Unicode 编码的书体给 `image`，
路径相对于 `public/`，并登记在 `public/glyphs/CREDITS.md`：

```ts
{ script: 'hieratic', image: 'glyphs/hieratic/edwin-smith-papyrus.jpg', label: '僧侣体纸草' },
```

如果该字体在 Google Fonts 上有可用的 css2 子集，运行
`work/.venv/bin/python tools/build-glyph-paths.py`，脚本会把实际字形轮廓
缩放、居中、翻转 Y 轴后写入 `src/data/glyphPaths.ts`。轨道渲染时会自动使用
`${scriptId}:${char}` 对应的轮廓。没有轮廓的字符仍走淡变、缩放与平移的兜底方案。

字母场的同源槽位另有一份整表轮廓（`src/data/glyphAlphabets*.ts`），同一支脚本
一并生成。手工槽位的字符**必须**有轮廓：少一个，那一格就悄悄退回交叉淡变——
不报错，只是不再形变，是最难被发现的一种退化。`tools/audit-rosters.mjs` 因此
把"手工槽位的字符都有轮廓"当硬约束，缺哪个直接列出来（确实没有字形的写进
`OUTLINE_EXEMPT` 并说明原因）。这条约束是因为真正的退化才补上的：霍杰基文的
短 i（𑉀）与婆罗米的 𑁵 加进字表后没重跑生成脚本，两份轮廓包一直停在旧版本。

编写时的三个约定：

- **每条轨道都要写 `source`。** 出处写清依据哪份资料（条目正文、Unicode 提案、
  对照表都行）。校验脚本把空 `source` 当错误：核对不了的链条不上线。
- **站点要有名字和音值。** `label` 出现在舞台标题上，`phonetic` 让读者知道
  这两站在音上是不是同一个东西。
- **古字形请标注为示意性重构。** 目前带 `path` 的古字形是为了演示演变机制
  而重绘的近似形，不等于古文字学摹本。将来会把它们替换为带出处的精确轮廓。

`path` 模式下还有一些细节值得知道：

- 两个站点子路径数量不一致时，落单的子路径会**原地收缩成点或从点长开**，
  配合 `fill-rule: nonzero`，表现为一笔消失或出现；
- 起笔点不同不会出错（弧长采样会把每段路径重新参数化），
  但**笔画走向合理**的路径会得到更自然的过渡。

## 形变引擎是怎么工作的

`src/lib/morph.ts` 是一个不到 150 行、零依赖的 SVG 路径形变实现。
它做的事和 PPT 的"平滑过渡"在同一原理上，只是参数由我们掌控：

```
path A ─→ splitSubpaths ─→ 每条子路径沿弧长采样 N+1 个点 ─→ PreparedGlyph
path B ─→ splitSubpaths ─→ 每条子路径沿弧长采样 N+1 个点 ─→ PreparedGlyph
                                │
                                ├─ 按重心 / 面积 / 包围盒配对子路径
                                ├─ 闭环起点做最佳错位对齐
                                ├─ 落单轮廓原地收缩成点 / 从点长开
                                ↓
       interpolatePath(A, B, t) → 逐点线性插值 → 生成中间 path（M…L…Z）
```

几个刻意的选择：

- **弧长采样**而不是按控制点配对。两端 path 的命令结构可以完全不同
  （一条是 `C` 曲线，一条是 `L` 直线），插值时只认几何。
- **子路径按几何配对**，而不是按数组下标。字形常由许多互不相连的笔画和
  内孔组成；按重心、面积与包围盒匹配，能让局部笔画就近变形，
  不至于让顶部的小点去追逐整条大弧。
- **闭环起点对齐**。每条轮廓都尝试所有整数错位，选择采样点总距离最短的起点，
  减少形变途中的自旋与打结。
- **落单轮廓原地收放**。A 多出的笔画收缩到自身重心，B 多出的笔画从自身重心
  长开；配合 `fill-rule: nonzero`，表现为一笔消失或出现，而不是跨字拉线。
- **不用第三方形变库**。`flubber` 一类库能做同样的事，但自己实现才能完全
  控制采样密度、子路径配对与异常输入——而且这个引擎本身是这个项目
  最想让别人复用的部分。
- **有兜底**。拿不到 SVG 几何接口（无 DOM 环境、病态路径）时，退回到
  "读出所有坐标数字当折线均匀采样"，精度下降但不会白屏。

目前 37 条血统轨道上的字符站点，能取到可靠轮廓的会走真·几何形变；
隶书、僧侣体、世俗体这类只能看历史图版的站点则保留 **交叉淡变 + 下一站残影**，
不会用现代字体顶替。其余没有轮廓的站点同样走淡变、缩放与平移的兜底方案，
所以任何文字都能有"沿街往前走"的连续感。

## 字形来源：宁缺毋滥

每个字形都必须能回答"它从哪来"。答案只允许三种，统一由
`src/data/glyphSources.ts` 说了算：

1. **字体** —— 确有该书写体系字面的那款字体。Google Fonts 的 Noto 系列按需注入
   一个 `<link>`，历史书体用自托管子集（`public/fonts/`），例如甲骨文用镜原甲骨
   字库、小篆用開元小篆。字库没收的字留在覆盖表外面，直接不画。
2. **图版** —— 没有可用字库、也没有（或几乎没有）Unicode 编码的体系，改用有
   出处的实物照片或摹本（印度河、原始埃兰、玛雅 …）。图版逐张登记作者与授权，
   同步写在 `public/glyphs/CREDITS.md`。
3. **留空** —— 两者都没有时不画。宁可空着，也不让宋体冒充甲骨文。

所以"隶书用宋体显示""僧侣体拿楷体顶替"这类事在结构上就被挡住了：

- 渲染点先问来源是哪一类，字体来源必须有字族，图版来源必须有图；
- `verifyFont()` 用 `document.fonts.load()` 兜底探测，私有区（PUA）直接判无字形；
- 拿不到字形就渲染一枚**码位名片**（`U+10600 · 字库未收`），而不是豆腐块。

`tools/audit-rosters.mjs` 另守一件事：手工同源槽位的每个字符都要有矢量轮廓。
槽位加了、轮廓包没重跑，字母场会从那一段起悄悄退回交叉淡变——这条体检就是拿来
抓这种"不报错、只是不再形变"的退化的。

`tools/audit-glyph-sources.mjs` 把这些规矩钉进 `npm run validate`：逐个体系核对
来源可定性、图版文件真实存在且登记在册、字母场的每一格与轨道的每一站都能落到
字体 / 图版 / 轮廓三者之一（**不允许**出现"没有字族"这种会掉进浏览器系统字体栈
的情况）；同时核对轨道轮廓包记录的取形字族与前端此刻渲染用的字族是否一致——
不一致说明来源改了却没重跑 `tools/build-glyph-paths.py`，形变的两端会画成两种
字面。兜底字族表只留一份（`src/data/fontFallback.ts`），Python 侧现场读它。

缺字形这件事本身，也是这些文字流传现状的一部分，值得被看见。

字面的**设计**对不对，是另一回事：覆盖表只能说"这款字族里有这些码位"，说不
出"画的是不是这套文字"。这一层由人工核实，结论落在 `tools/font-verdicts.tsv`
（一行一个体系，见上文"字体审看台"），并由 `npm run validate` 守着——新体系
必须补记录，已知画错的字体会直接让构建失败。

想为某种文字补上字形，有两条路：
打包一个自带子集的 `woff2`（注意字体许可），
或者按"血统轨道"的做法给出带出处的矢量轮廓。

## 设计说明

视觉方向是**考古图录 × 星图**：深墨底、朱砂点、青铜线，
取自所写之物本身的材质——墨、朱砂印、青铜锈、宣纸、藤黄。
刻意避开了"深蓝底 + 紫色渐变 + 玻璃卡片"这套默认科技皮肤，
因为那套皮肤和泥板、竹简、棕榈叶没有任何关系。

字体分三个角色，各有分工：

| 角色 | 字体 | 用在哪 |
| --- | --- | --- |
| `--display` | 宋体 / Songti SC → Noto Serif SC | 标题、文字名：明代刻本的骨架 |
| `--antique` | Cardo → Iowan Old Style | 年代、码位、英文名：古典学排印的手抄本味 |
| `--body` | 苹方 / PingFang SC → Noto Sans SC | 正文：只负责读起来不费力 |

唯一的"响"色是朱砂（`--cinnabar`），只给当前状态——选中的节点、
激活的标签、正在变形的那个字形。别的颜色一律压低饱和度，
让百余个节点在深色底上像一张手工上色的地图，而不是一堆霓虹灯。

改设计时请从 `src/index.css` 的令牌入手，不要在各个组件里写死颜色。

## 部署

构建产物是纯静态文件，可以直接丢到任何静态托管：

```bash
npm run build && ls dist/
```

- **Vercel / Netlify / Cloudflare Pages**：构建命令 `npm run build`，输出目录 `dist`。
- **GitHub Pages**：线上站点 <https://jewelroam.github.io/Glyph-Atlas/>。
  仓库 Pages 的发布源设为 **GitHub Actions**；推送 `main`（或在 Actions 页手动触发）后，
  `.github/workflows/deploy.yml` 执行 `npm ci` 与 `npm run build`，
  再用 `actions/upload-pages-artifact` 与 `actions/deploy-pages` 发布 `dist/`。
- **子路径部署**：项目站点不在域名根目录，因此 `vite.config.ts` 里
  `base = '/Glyph-Atlas/'`，改名或改路径时要同步这个常量；
  本地 `npm run dev` 仍从根路径提供服务。
- 页面用 Google Fonts 作为字形来源，离线或内网部署时请自行镜像字体。

## 数据范围与已知边界

**当前数据**

- 总表共 194 条记录，其中 193 个书写体系进入演化图；
- 独立起源包含苏美尔、埃及、中国、印度河、中美洲等已知起点，以及起源仍有争议的候选体系；
- 字母、音节文字与元音附标文字按主要谱系收录，覆盖历史文字、现役文字和未破译文字；
- 语素文字包含汉字系的甲骨文、金文、篆书、隶书、楷书等阶段，以及假名、女书、契丹文等衍生体系；
- 奇普等非文字记录保留在总表中，不进入演化图，也不计作独立起源。

**已知边界（欢迎纠正）**

- 带 `path` 的古字形是**示意性重构**，用于演示机制，不是精确摹本；
- 年代是约数，学界分歧之处按主流观点取值；
- 谱系分区（十二个泳道）是为了可读性做的简化，
  真实的接触、混用与多重影响比树状图复杂；
- 未破译文字的归属（例如线形文字 A 与克里特象形文字的关系）仍在研究中。
- 字母场的对照表只收**能接回谱系的字母**：词尾形与位置变体（希伯来、叙利亚、
  蒙古这类）、大小写、以及与上下游都对不上的附加字母都不进表。校验脚本会把
  每家"字形样本数 / 对照表格数"打印出来，差额主要来自这些变体形与附加字母，
  不是把字母算丢了。
- 吕基亚 → 卡里亚这一段不做整表形变：卡里亚字母与希腊音值的对应至今没有定论，
  两家的字表整批进出，不硬凑"原地变形"（74 段字母场过渡里只有这一段如此）。
- 窄屏下图谱仍然拥挤：横轴被压到约三分之一，多数标注会被折叠。
  图谱是为桌面 / 横屏设计的视图，手机上更适合看总表与街景。

## 贡献

数据和代码都欢迎提交。

- 新增字形轨道 → 改 `lineages.ts`：`path`、`char` 或 `image` 三选一，并写明 `source`
- 修正史实 / 年代 → 请附上来源，方便复核
- 提交前请跑 `npm run check`
